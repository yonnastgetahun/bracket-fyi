# Phase 2 integration packet map

Read-only inventory basis: approved `bracket-fyi-spec-v1.0.md`, `phase-2-orchestrated-execution-plan.md`, and `phase-2-evidence-ledger.md` (2026-10-27). This map is an execution ordering and code ownership proposal, not closure evidence. E1–E8 and P2/P5–P12 remain pending in the ledger. Concurrent provider-repair and window-skeptic work are excluded; their outputs must be integrated only after their owners report stable contracts.

## Reusable architecture

Build one event-runtime pipeline, not nine apps: immutable `EventEdition`/versioned graph + typed market/outcome definitions → validated provider/manual evidence → canonical result projection with override provenance → shared lock/reconciliation/score services → generic league entry/pick/result/leaderboard UI driven by catalog/template metadata. Keep event-specific logic as small rule modules (`derive`, `validate`, `score`) and catalogs; use adapters for provider payloads. Shared lifecycle, auth, persistence, notification, operator controls and browser journey harness must not branch into event-specific copies. Templates are nine configurations across eight families (UCL, NFL, NCAA, NBA, WWC, MLB, CFP, Oscars); NBA Play-In is a distinct competition component, not an event/template clone.

Existing useful seams: `lib/events/outcomes.ts` typed result algebra; `derivation.ts` series, Play-In, reseeding and graph validators; `windows.ts` lifecycle/window rules; `repository.ts` persistence seam; `catalog.ts` edition/market registry. `app/l/[league_id]/data/route.ts` and league pages/routes are current app boundary; `app/api/admin/result/route.ts` is legacy manual result ingress and must bridge compatibly. `lib/ingestion/orchestrator/` and `run-ledger-repository.ts` provide orchestration/run-ledger foundation. `scripts/local-event-runtime.py` is the local-only runtime launcher. Do not claim these are integrated merely because helpers exist.

## File ownership and seams

Keep single-writer ownership: integration owner owns shared `lib/events` contracts, scoring bridge, lifecycle/reconciliation and cross-family tests; provider builders own only their adapter/HTTP files and isolated adapter tests; event builders own isolated rule/catalog files; UI builder owns generic components and browser tests; template builder owns template data/seeder; security/window owners retain their assigned files until independent acceptance. Migration authorship stays with the integration owner and must be additive. Routes should remain thin: authenticate/scope, parse DTO, invoke service, serialize allowlisted DTO. Do not put event rules in Next route handlers or UI components.

Inspect before adding: `app/api/admin/result/route.ts` (manual result compatibility), `app/l/[league_id]/data/route.ts` (scoped league read), `app/api/admin/{lock,unlock}.` routes (legacy lifecycle interaction), `lib/ingestion/orchestrator/` (run lifecycle), `scripts/local-event-runtime.py` (safe local env). Missing seams are the single typed ingestion-to-evidence dispatcher, shared scoring/result projection invocation, durable override/reconciliation state machine, durable notification-intent consumer, generic template seeder, cross-family synthetic journey runner, and browser acceptance harness. Avoid treating existing route/repository presence as proof of those bridges.
